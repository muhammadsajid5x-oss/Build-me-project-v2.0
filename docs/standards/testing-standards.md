"# Testing Standards"
""
"## Purpose"
""
"These standards define how testing is planned, written, executed, and validated in the Build Me project."
""
"The goal is to provide reliable evidence that the system works correctly, handles failures safely, and meets its requirements."
""
"## Testing Principle"
""
"> Test the behavior that matters. Use the appropriate test level to provide reliable evidence."
""
"## 1. What Must Be Tested"
""
"Testing should cover behavior required by the requirement and acceptance criteria."
""
"Where applicable, test:"
"- Normal functionality"
"- User interactions"
"- Error handling"
"- Validation"
"- Empty states"
"- Loading states"
"- Boundary conditions"
"- Important edge cases"
"- Authentication and authorization"
"- Security-sensitive behavior"
"- API behavior"
"- Database behavior"
"- Critical user journeys"
"- Performance-sensitive behavior"
""
"## 2. Testing Levels"
""
"### Unit Tests"
""
"Use Jest for TypeScript and JavaScript unit tests."
""
"Use pytest for Python unit tests where Python is used."
""
"Unit tests should verify isolated:"
"- Functions"
"- Utilities"
"- Business logic"
"- Validation logic"
"- Data transformations"
""
"### Component Tests"
""
"Use Storybook + Jest for appropriate UI component testing."
""
"Component tests should verify:"
"- Rendering"
"- User interactions"
"- Component states"
"- Loading states"
"- Empty states"
"- Error states"
"- Important accessibility behavior"
""
"### Integration Tests"
""
"Use Jest + SuperTest for appropriate API and service integration testing."
""
"Use pytest for appropriate Python integration testing."
""
"Integration tests should verify:"
"- Service interactions"
"- API behavior"
"- Request and response handling"
"- Validation"
"- Error handling"
"- Authentication and authorization where applicable"
"- Relevant database interactions"
""
"### API Tests"
""
"Use SuperTest for appropriate HTTP API testing in the TypeScript/Node.js application."
""
"API tests should verify:"
"- HTTP methods"
"- Status codes"
"- Request validation"
"- Response structure"
"- Error responses"
"- Authentication"
"- Authorization"
""
"### End-to-End Tests"
""
"Use Cypress for appropriate complete user journeys."
""
"E2E tests should verify:"
"- Critical user workflows"
"- Navigation"
"- Important user interactions"
"- Successful journeys"
"- Important failure journeys"
"- Critical acceptance criteria"
""
"### Performance Tests"
""
"Use k6 for appropriate performance and load testing."
""
"Performance tests should be used when performance is an important requirement or risk."
""
"Measure relevant:"
"- Response time"
"- Throughput"
"- Error rate"
"- Load behavior"
"- Resource-sensitive operations where applicable"
""
"### Security Tests"
""
"Use OWASP ZAP and appropriate API security tests where applicable."
""
"Security testing should consider:"
"- Authentication"
"- Authorization"
"- Input validation"
"- Access control"
"- Sensitive data exposure"
"- Common web vulnerabilities"
"- API security boundaries"
""
"## 3. When Tests Are Required"
""
"Tests are required when:"
"- New behavior is introduced."
"- Existing behavior is changed."
"- A bug is fixed."
"- Business logic changes."
"- API behavior changes."
"- User-facing behavior changes."
"- Security-sensitive behavior changes."
"- A regression risk exists."
""
"Not every change requires every testing level. Select tests based on the behavior and risk being validated."
""
"## 4. Test Naming"
""
"Test names should clearly describe the behavior being verified."
""
"Prefer names that explain:"
"- What is being tested"
"- The condition or scenario"
"- The expected result"
""
"Example:"
""
"test('returns an error when the required email is missing')"
""
"Avoid vague names such as:"
""
"test('works')"
""
"## 5. Local Test Execution"
""
"Developers must run relevant tests locally before creating or updating a Pull Request."
""
"At minimum, run the test commands required by the affected application or package."
""
"Typical project commands may include:"
""
"pnpm test"
"pnpm test:unit"
"pnpm test:e2e"
""
"Use the project's actual package scripts and documented commands rather than assuming a command exists."
""
"## 6. CI Test Execution"
""
"CI must run the project's required automated validation."
""
"CI should include appropriate:"
"- Unit tests"
"- Component tests"
"- Integration tests"
"- API tests"
"- E2E tests"
"- Type checking"
"- Linting"
"- Build validation"
""
"Not every CI run must execute every test suite if the project's CI design intentionally separates test stages. Required checks must still run before the relevant merge or deployment gate."
""
"## 7. Test Quality"
""
"Tests should be:"
"- Reliable"
"- Deterministic"
"- Easy to understand"
"- Focused"
"- Maintainable"
"- Fast where practical"
"- Independent where appropriate"
""
"Avoid:"
"- Weak assertions"
"- Unnecessary duplication"
"- Tests that depend on execution order"
"- Hard-coded environment-specific values"
"- Flaky timing assumptions"
"- Tests that pass without meaningfully validating behavior"
""
"## 8. Test Evidence"
""
"Passing tests are evidence for the behavior they actually validate."
""
"A test suite must not be treated as proof of functionality that it does not cover."
""
"Review test results before accepting a change."
""
"## 9. Definition of Done"
""
"Where applicable, a feature is not considered complete until:"
"- Required automated tests are created."
"- Relevant tests pass."
"- Test failures are investigated."
"- Required CI checks pass."
"- Critical acceptance criteria are covered."
"- Regression risks have been considered."
""
"## Key Principle"
""
"> Automated tests provide evidence. The Technology Owner remains responsible for deciding whether the evidence is sufficient."
)
